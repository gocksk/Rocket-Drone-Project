300 km/h 테일시터 로켓 쿼드의 **개념설계 사이징 코드**입니다.

설계점 하나를 넣으면 성적표(C1–C8)와 합격조건(g1–g9)이 나옵니다.
이걸 수천 개 후보에 반복해 최적 설계점을 찾는 것이 최종 목표입니다.

## 지금 어디까지 왔나

**구조는 완성됐고, 물리는 검증 전입니다.** 이 둘을 섞어 읽으면 안 됩니다.

| | 상태 |
|---|---|
| 파이프라인 | ⓪①② 전 구간 실행됨. 스텁 없음 — 모든 g·C가 실제 계산값 |
| 실행 속도 | 설계점당 **3.1 초** (측정 완료) |
| 수치 건전성 | 수렴·순수성·연속성 측정 완료 (P7 게이트) |
| **계수** | **151개 중 116개가 TBD** — 실측·시험으로 확정해야 함 |
| **물리 검증** | ATM(ISA 대조)·GEOM(손계산)·WGHT(16종) 외에는 **미검증** |

## 핵심 아이디어: 부품은 고르는 게 아니라 계산된다

보통의 드론 설계는 "이 모터 쓰고 이 배터리 쓰자"로 시작합니다.
이 코드는 반대입니다.

> 요구조건(300 km/h, 3 km, 4기 로터)을 만족하는 **최소 스펙을 코드가 풀고**,
> 그 위의 여유만 설계변수(`k_mot`, `k_E`)로 탐색합니다.

그래서 `kv`·연속출력·`E_batt`는 설계변수가 **아닙니다**. 계산되어 나옵니다.

문제는 이게 **닭과 달걀**이라는 점입니다. 무거우면 모터가 커지고, 모터가 커지면
무거워집니다. 그래서 MTOW를 반복해서 수렴시킵니다 — 그게 아래 ①입니다.

---

## 실행 흐름 — ⓪①②

```
⓪ 전처리          무게와 무관한 것들. 설계점당 딱 1회.
   atm.run → geom.hull → aero.run → prop.build_map

① 사이징 루프      MTOW 하나를 수렴시킨다. 12회쯤 돈다.
   resp_of(MTOW):
     prop.size_motor(MTOW, …)      → m_mot     요구를 만족하는 최소 모터
     miss.required_energy(MTOW, …) → m_batt    임무를 완주하는 최소 배터리
     strc.run(MTOW, …)             → W_str     하중을 견디는 최소 구조
     return 이 셋의 합
   wght.converge(m_fixed, resp_of)

② 후처리          수렴한 무게로 딱 1회.
   geom.layout → geom.check_fit → prop.evaluate
   → miss.achieved_range → stab.run → cost.run
```

`m_fixed`는 MTOW와 무관한 무게(탑재체·항전·프롭)이고, `resp_of`가 돌려주는 것이
MTOW에 **반응하는** 무게입니다. 둘이 만나는 점이 수렴 해입니다.

### `resp_of`는 순수 함수여야 합니다

같은 MTOW를 넣으면 **항상** 같은 값이 나와야 합니다. 캐시·전역변수·난수 금지.
모듈 안의 순환은 결정론적 이분법으로 닫습니다.

이게 깨지면 배치 실행에서 설계점끼리 결과가 오염됩니다. 겉으로는 잘 도는 것처럼
보이는데 DOE 결과만 조용히 틀립니다. `validation/p7_gate.py`가 이걸 검사합니다.

## 합격조건 g1–g9

**음수면 불합격**입니다. 그런데 성격이 셋으로 나뉘고, 섞어 읽으면 오독합니다.

### ⓪ 성립 조건

| | | |
|---|---|---|
| g1 | 순항 성립 | 프롭 피치속도가 순항속도를 낼 수 있나 |

### ① 사이징 잔차 — **0에 붙는 게 정상**

| | | |
|---|---|---|
| g2 | 팁 마하 | 프롭 팁이 음속 한계 안인가 |
| g3 | 열 한계 | 모터 권선 온도가 한계 안인가 |
| g4 | 사이징 수렴 | MTOW 루프가 수렴했나 |

⚠ **여기가 함정입니다.** `size_motor`는 트림·팁마하·열을 *동시에 만족하는 최소*
질량을 찾은 뒤 `k_mot`을 곱합니다. 그러면 구속하는 조건은 `k_mot = 1.0`에서
**정의상 0에 붙습니다.**

측정해 보니 7개 설계점 전부 **열이 구속**했고 g3 = +0.000~+0.004였습니다.
g3이 작다고 "빡빡한 설계점"인 게 아닙니다. 그건 사이징의 출력입니다.

### ② 품질 조건 — 실제 스크리닝

| | | |
|---|---|---|
| g5 | 구조 응력 | 핀 루트가 버티나 |
| g6 | 부품 내장 | 부품이 동체 안에 들어가나 |
| g7 | 프롭 클리어런스 | 프롭이 서로/동체에 안 닿나 |
| g8 | 직진 안정 | 정적 안정여유가 충분한가 |
| g9 | 천이 조종 | 수직↔수평 전환 때 조종 권한이 있나 |

⚠ **g8과 g9는 서로 밉니다.** 안정을 키우면 조종이 어려워집니다
(`M_dist ∝ SM`). 합격 밴드가 좁은 대각선입니다.

## 성적표 EC (C1–C8)

| EC | 지표 | 방향 | 가중치 |
|---|---|---|---|
| C3 | 속도 여유 `V_max/V_cr` | ↑ | **33.7 %** |
| C1 | 총 무게 MTOW | ↓ | 23.0 % |
| C8 | 보관 전장 | ↓ | 13.5 % |
| C2 | 달성 항속거리 | ↑ | 11.1 % |
| C5 | 조종 각가속도 | ↑ | 10.4 % |
| C7 | 취득비 | ↓ | 4.2 % |
| C4 | 설계 하중배수 | ↑ | 2.9 % |
| C6 | 호버 소음 | ↓ | 1.2 % |

C3이 1등인 이유: 300 km/h 달성은 사이징이 보장하므로, 그 위의 여유는
로드맵(300 → 400 → 500 km/h)에서 **다음 판의 실현 가능성**이라는 실제 가치를
갖습니다. 제약으로만 흡수하면 305와 380이 같은 점수가 됩니다.

## DOE — 설계공간 훑기

`main.py`가 설계점 **하나**를 평가한다면, `doe/`는 그걸 수백~수만 개 반복합니다.
**계산은 `doe/`에 없습니다** — `main.evaluate()`를 그대로 부르고, 표본 생성·병렬
실행·로그·재개만 책임집니다. 사이징 경로는 한 줄도 다르지 않습니다.

### 창으로 돌리기

```bash
python -m doe.gui
```

| 구획 | 하는 일 |
|---|---|
| 탐색 상자 | `smoke` / `screen` 선택 → 축 표가 그 값으로 채워집니다 |
| 축 범위 | 11축 하한·상한. **비어 있으면 빨간 글씨**로 표시되고 실행이 막힙니다 |
| 실행 설정 | 표본 수·시드·복제 비율·워커·셀 수·출력 경로·옵션 체크 |
| 버튼 | 상자 검사 · 배치 실행 · 중단 · 분석 보기 |
| 출력 | 조립된 명령줄 · 진행률 막대 · 로그 |

창은 `python -m doe.run …` 명령을 조립해 자식 프로세스로 띄울 뿐입니다. 조립된
명령이 창에 그대로 찍히므로 **복사해서 터미널에 붙이면 똑같이 돕니다** (CI·원격은
그렇게 씁니다). 창에서만 되는 실행을 만들지 않는다는 뜻입니다.

### 터미널로 돌리기

```bash
python -m doe.run --box smoke --n 30
```

```bash
python -m doe.report runs/smoke.jsonl
```

### 탐색 상자란

표본을 뿌릴 각 설계변수의 `[하한, 상한]` 묶음입니다. 축마다 구간이 하나씩이니
11차원 직육면체가 되고, 그래서 "상자"입니다. LHS(라틴 하이퍼큐브)가 그 안에만
점을 뿌립니다.

| 상자 | 무엇 | 쓸 때 |
|---|---|---|
| `smoke` | 공칭점 ±4 % (P7 연속성 스윕과 같은 폭) | 배관 확인. 물리 결론용이 아닙니다 |
| `screen` | ICD §2가 범위를 준 5축만 채워져 있고 **6축이 비어 있음** | 1차 스크리닝. 빈 축을 `--set`으로 채워야 돕니다 |

`screen`에서 비어 있는 축은 `d_body` `lambda_body` `S_fin` `x_fin_ratio` `AR_fin`
`pd_prop`(상한)입니다. ICD §8 B-2 미확정이라 **값을 지어넣지 않았습니다.** 그 상태로
실행하면 런처가 어느 축이 비었는지 찍고 멈춥니다.

> **상자는 합격 영역이 아닙니다.** 너무 넓으면 표본 대부분이 탈락으로 버려지고
> (§11-48: `d_body`·`x_fin`·`k_mot`은 ±4 %만 움직여도 9점 중 4점을 잃습니다),
> 너무 좁으면 최적점이 상자 벽에 붙어 나옵니다 — "여기가 최적"이 아니라 "여기가
> 내가 허락한 끝"이라는 뜻이라 결론이 되지 못합니다.

**`x_fin`은 비율로 뿌립니다.** 표본 공간의 축은 `x_fin`(절대 위치 [m])이 아니라
`x_fin_ratio = x_fin / l_body`입니다. 전장은 `d_body·lambda_body`에서 나오므로,
절대 위치로 뿌리면 "전장 0.6 m 기체에 핀을 0.8 m 지점에" 같은 조합이 대량으로
나오고 그 표본은 ⓪ GEOM에서 통째로 죽습니다.

| 축 범위 | `--set d_body=0.07:0.11` | 표본이 뿌려지는 구간 | **유효율**과 EC 분포가 통째로 달라집니다. 보고 §4의 4분위 합격률이 한쪽 끝만 낮으면 그 방향으로 너무 넓다는 뜻입니다 |
| 축 좁히기 | `--focus k_mot=0.5` | 공칭점 중심으로 폭을 절반으로 | 칼날축을 촘촘히 보는 손잡이입니다. LHS는 모든 축을 같은 층수로 자르므로, "촘촘히"는 결국 폭입니다 |
| 표본 수 | `--n 500` | 수준당 표본 수 | 시간이 **선형**으로 늡니다. 보고 §4의 판정은 200점 이상에서만 붙습니다 (그 아래는 잡음) |
| 셀 수 | `--n-ser 4,6,8` | 수준별로 배치를 나눔 | 총 표본 = `n × 수준 수`. 수준마다 시드를 갈라 서로 다른 표본을 뽑습니다 |
| 시드 | `--seed 1` | 같은 상자에서 다른 표본 | **같은 시드 = 같은 목록.** 로그 재현과 재개가 여기 걸려 있습니다 |
| 복제 비율 | `--dup-frac 0.01` | 같은 설계점을 한 번 더 넣음 | 보고 §5 **순수성** 판정. 병렬에서 설계점끼리 오염되면 두 행이 갈라집니다. 비용은 그 비율 그대로 |
| 워커 | `--workers 14` | 동시 프로세스 수 | 처리량이 거의 선형으로 늡니다 (SMT라 효율 55 % 정도) |
| Ŝ 분해 | `--split` | `resp_of`를 2회 더 호출 | `diag.S_split`(구조·모터·배터리 기여)이 생깁니다. **+16 % 시간. 수치 결과는 안 바뀝니다** |
| 이어 돌리기 | `--resume` | 로그에 있는 id는 건너뜀 | 중단된 배치를 이어서 돌립니다 |
| 덮어쓰기 | `--force` | 매니페스트 불일치 무시 | ⚠ 다른 상자의 행이 한 파일에 섞입니다. 웬만하면 `--out`을 바꾸세요 |
| 출력 경로 | `--out runs/이름` | 로그·매니페스트 파일명 | — |
| 검사만 | `--dry-run` | 평가 없이 상자·표본만 출력 | 8시간짜리를 걸기 전에 상자를 확인하는 용도 |

### 무엇이 나오나

```
runs/<이름>.jsonl           설계점 한 개 = 한 줄
runs/<이름>.manifest.json   상자·시드·커밋·constants 해시·실행 시각
```

로그 한 줄에는 설계변수 12개, `g1`–`g9`, `C1`–`C8`, 진단 변수 전부, `fail_code`,
`fail_stage`, 소요 시간이 들어갑니다. 형식이 JSONL인 이유는 진단 항목이 아직 계속
늘어나기 때문입니다 — 열이 고정된 CSV는 과거 로그와 붙지 않습니다.

**매니페스트가 없는 로그는 믿을 수 없습니다.** 상수가 TBD 투성이라 며칠 뒤 두
로그가 서로 다른 상수에서 나왔다는 사실을 모르면 결론이 통째로 오염됩니다.
`constants.py`가 이전 실행 이후 바뀌었으면 런처가 경고합니다.

`python -m doe.report <로그>`가 여섯 절을 냅니다.

| 절 | 내용 |
|---|---|
| 1 유효 표본 비율 | 합격률과 **탈락 사유 히스토그램** (사유 코드는 DOE 로그의 1급 데이터) |
| 2 게이트 | 게이트별 합격률·최소·중앙. **사이징(g1–g4)과 품질(g5–g9)을 나눠 찍습니다** |
| 3 성적표 | 합격 표본의 C1–C8 분포 |
| 4 축별 | 축을 4분위로 갈라 구간별 합격률 (200점 이상에서만 판정을 붙입니다) |
| 5 순수성 | 복제 쌍이 비트 동일한지 |
| 6 시간 | 설계점당 시간·누적 CPU 시간 |

### 읽을 때 조심할 것 세 가지

1. **`g2`·`g3`·`g4`를 "가장 빡빡한 게이트"로 읽지 마세요.** 사이징이 0으로
   몰아붙이는 잔차이지 설계점의 성질이 아닙니다 (§11-44). 실제 스크리닝은
   `g5`–`g9`에서 일어납니다.
2. **유효율은 설계의 성질이 아니라 상자의 성질입니다.** 상자를 넓히면 떨어집니다.
3. **EC 가중합 점수(§6.2)는 아직 없습니다.** C1–C8은 단위가 제각각이라 정규화가
   필요한데 기준이 미정입니다 — 표본 최소–최대냐 요구조건 기준이냐에 따라 순위가
   뒤집힙니다. 설계점 하나로는 원리적으로 못 내는 값이라 `evaluate`가 아니라
   분석 쪽 소관입니다.

## 알아둘 것 — 코드를 읽기 전에

측정으로 확인된 것들입니다. 모르고 보면 버그로 착각합니다.

**1. 무게 스노우볼의 87.5 %는 배터리입니다.**
모터 9.5 %, 구조 3.0 %. 구조를 깎아도 MTOW는 거의 안 줄어듭니다.

**2. 구조가 MTOW의 61 %입니다.**

| 항목 | 질량 |
|---|---|
| 구조 | 740.8 g |
| 배터리 | 216.2 g |
| 고정 (탑재·항전·프롭) | 158.2 g |
| 모터 ×4 | 103.9 g |
| **MTOW** | **1219.0 g** |

PLA 1.8 mm 벽과 10 mm 두께 핀이 이 크기에서 지배적으로 무겁습니다.
**응력이 아니라 프린트 가능성이 두께를 정하고 있습니다.** 재료 재검토가 필요합니다.

**3. 열이 이 기체의 진짜 구속 조건입니다.**
순항이 착륙 호버보다 뜨겁습니다 (구리손실비 5.8 > 대류비 5.2).
`k_mot`은 1.0이 사실상 하한이고, 0.99에서 g3 = −1.93으로 떨어집니다.

**4. `w_fill` 양자화가 계단을 만듭니다.**
핀 루트 보강 폭이 슬라이서 압출선 정수배로 떨어져 `W_str`이 743 mg씩 뜁니다.
현재 수렴 허용오차(1200 mg) 대비 여유가 **1.6배뿐**입니다.
`eps_conv`를 조이면 `limit_cycle`이 납니다 — 발산이 아니라 이산화입니다.

**5. `x_fin`은 MTOW에 전혀 반응하지 않습니다.**
±4 % 흔들어도 C1이 비트 단위로 같습니다. 대신 g8을 0.29 움직입니다.
**목적함수 기준 스크리닝으로는 절대 안 걸러집니다.** 제약 기준으로 따로 훑어야 합니다.

**6. 실현 가능 영역이 세 축으로 얇습니다.**
`d_body`·`x_fin`·`k_mot`은 ±4 %에서 9점 중 4점씩 탈락하고,
나머지 8개 변수는 한 점도 안 잃습니다. DOE 격자를 균일하게 깔면 표본이 낭비됩니다.

**7. AERO가 런타임의 56 %입니다.**
`aero.CD0`가 설계점당 146만 회 불립니다. ⓪ 모듈인데도 그런 이유는,
`run()`이 돌려주는 `F_drag`·`CL`이 MISS 적분과 PROP 트림 안에서 계속 불려서입니다.

## 기여 규칙

전부 상위 폴더의 `CLAUDE.md`에 있습니다 (저장소 바깥). 핵심 넷:

**1. 인터페이스는 계약입니다.**
`interfaces.py`의 시그니처는 ICD §5가 정한 것입니다. 바꿔야 한다고 판단되면
코드를 고치지 말고 **먼저 논의**하세요. ICD를 고치는 게 먼저입니다.

**2. 숫자를 코드에 박지 않습니다.**
모든 상수는 `constants.py`에서 import합니다. ICD §3에 없는 상수를 새로
만들었다면 `# ICD외`로 표시하고 보고합니다.

**3. 스텁은 정직하게 표시합니다.**

```python
raise NotImplementedError("PROP.solve_point — 트림 연립 미구현")
return 0.0  # [스텁] 실제 값 아님 — BEMT 구현 후 교체
```

**그럴듯한 물리값을 지어내 채우지 않습니다.** 나중에 구현된 것으로 착각하게 되고,
그게 이 프로젝트에서 가장 비싼 실수입니다.

**4. "완료"를 두 가지로 구분합니다.**

- **구조 완료** — 실행되고 시그니처가 맞는다
- **검증 완료** — 알려진 정답과 대조했다 (**무엇과** 대조했는지 명시)

테스트가 통과했다고 물리가 맞는 건 아닙니다.

### `modules/wght.py`는 손대지 마세요

이미 검증된 자산입니다. 수렴 상태머신의 분기 조건은 한 줄도 바꾸지 않습니다.

### GitHub 흐름

`main`에 직접 푸시 금지. `feat/<모듈>` · `fix/<내용>` · `docs/<내용>`로 브랜치를 땁니다.
커밋 제목에 모듈명을 답니다 (`[PROP] build_map BEMT 구현`).
미결 사항은 커밋 메시지에 `[확정 필요]`로 남깁니다.

머지는 **merge commit** 또는 **rebase**. **squash는 쓰지 않습니다** —
`[확정 필요]` 기록이 묻힙니다.

PR 전에 `python main.py`가 에러 없이 끝나는지 확인합니다.
합격/불합격은 상관없고 **중간에 죽지만 않으면** 됩니다.
PR·푸시마다 [CI](.github/workflows/ci.yml)가 같은 검사와 WGHT 16종을 자동으로 돌립니다.

> CI가 있는 이유: 각자 자기 파일만 고치므로 git 충돌은 잘 안 납니다. 정작 위험한 건
> **의미 충돌**입니다 — STRC가 슬라이서 계수를 실측값으로 바꾸면 WGHT의 수렴 강도가
> 달라지는데, 파일이 달라 충돌도 안 나고 각자 `python main.py`도 잘 돕니다.
> 합쳐놓고 돌려야만 보입니다.
